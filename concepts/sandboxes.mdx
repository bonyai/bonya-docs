A **sandbox** is the resource everything else in the API is scoped to. Sessions, exec, files, previews, snapshots and jobs all operate on a sandbox identified by its `id`.

## Identity

A sandbox gets a server-assigned `id` such as `sb-bpyk22c3ei3hfx`, which is the only identifier every other operation accepts. A sandbox can also have a `name`, but names are a display label, not an identifier:

- `name` is optional on create (up to 80 characters). If you omit it, the service generates a friendly one such as `winter-canyon-278e`.
- `name` is **not unique**. Several sandboxes can share a name, so look one up by `id` when it matters.

<Note>
Always key off `id` in code you write against this API. Treat `name` as something to show a human.
</Note>

A sandbox looks like this:

```json
{
  "id": "sb-2ofternj7d98tk",
  "name": "scratch",
  "organization_id": "org-muzwhim6z9e1s5",
  "template_version": "bonya-dev-x86_64-xeon8358-1c1024m-v1",
  "state": "running",
  "generation": 1,
  "vcpus": 1,
  "memory_mib": 1024,
  "user_layer_bytes": 10737418240,
  "created_at": "2026-11-09T23:00:32.645482Z",
  "started_at": "2026-11-09T23:00:32.691990029Z",
  "network": { "mode": "open" }
}
```

A sandbox runs as `root` with `HOME=/root`, starting in `/`.

## Lifecycle states

A sandbox's `state` is one of:

| State | Meaning |
| --- | --- |
| `creating` | The sandbox is being provisioned. |
| `running` | The sandbox is up and reachable for exec, sessions, files, and previews. |
| `cooling` | The sandbox is going idle. |
| `warm` | Paused with its memory kept on its node. The fastest wake. |
| `cold` | Saved to storage and its node freed. No running cost, a slower wake with fresh processes. |
| `waking` | Coming back to `running`. |
| `failed` | Provisioning or a transition failed. `failure_reason` says why. |
| `deleting` | Being torn down. |
| `deleted` | Deleted. A tombstone, never returned by list. |
| `lost` | The sandbox's host was lost. |

Idle sandboxes pause on their own, and traffic wakes them. You can also drive the lifecycle explicitly:

<CodeGroup>
```shell cURL
# pause (stage: warm or cold)
curl -s -X POST "https://api.bonya.ai/v1/sandbox/$SANDBOX_ID/pause" \
  -H "Authorization: Bearer $BONYA_API_KEY" -H "Content-Type: application/json" \
  -d '{"stage": "warm"}'

# keep awake for 30 minutes; also wakes a paused sandbox
curl -s -X POST "https://api.bonya.ai/v1/sandbox/$SANDBOX_ID/keepalive" \
  -H "Authorization: Bearer $BONYA_API_KEY" -H "Content-Type: application/json" \
  -d '{"for": "30m"}'
```

```ts TypeScript
await sandbox.pause("warm");
await sandbox.keepalive(30 * 60); // also wakes a paused sandbox
```

```python Python
sandbox.pause("warm")
sandbox.keepalive(30 * 60)  # also wakes a paused sandbox
```

```go Go
err := sandbox.Pause(ctx, bonya.PauseWarm)
until, err := sandbox.Keepalive(ctx, 30*time.Minute)
```
</CodeGroup>

There is no separate resume endpoint: **keepalive wakes a paused sandbox**. A sandbox paused explicitly is not woken by exec or preview traffic, so wake it with keepalive first. The CLI's `bonya console` wakes the sandbox for you. **MCP:** `sandbox_pause` and `sandbox_keepalive`.

## Creating a sandbox

<CodeGroup>
```shell cURL
curl -s -X POST "https://api.bonya.ai/v1/sandbox?wait=ready" \
  -H "Authorization: Bearer $BONYA_API_KEY" \
  -H "Content-Type: application/json" \
  -d '{"name": "scratch"}'
```

```shell CLI
bonya create scratch
```

```ts TypeScript
import { Bonya } from "@bonya-ai/bonya";

const client = new Bonya();
const sandbox = await client.createSandbox({ name: "scratch" });
```

```python Python
from bonya import Bonya

with Bonya() as client:
    sandbox = client.create_sandbox(name="scratch")
```

```go Go
client, err := bonya.NewClient()
if err != nil {
    log.Fatal(err)
}
sandbox, err := client.Create(ctx, bonya.CreateOptions{Name: "scratch"})
```
</CodeGroup>

**MCP:** `sandbox_create`.

An empty body creates a sandbox from the deployment's default image. The request body accepts:

| Field | Description |
| --- | --- |
| `name` | Display label, up to 80 characters. |
| `template_id`, `template_revision` | Start from a saved [template](/concepts/templates). |
| `image` | A public OCI image reference (tag or digest). Cannot be combined with `snapshot`, `template_id` or `template_version`. |
| `snapshot` | Restore from a [snapshot](/concepts/snapshots). |
| `gpu` | `{ "type": "...", "count": 1 }`. Requires an `image` (or an image template). See [GPUs](#gpus). |
| `network` | A network policy (see [below](#network-policy)). |
| `env` | Environment variables. |
| `secret_sets` | Secret set **names** injected as environment variables. |

By default, create returns **202 Accepted** with the sandbox still `creating`. Pass `?wait=ready` to block until it is running and get **201 Created** instead. Both return the sandbox object itself.

<Note>
The REST default is non-blocking, but the TypeScript and Python SDKs default to waiting until the sandbox is ready, like the CLI. Pass `wait: "none"` / `Wait.NONE` to return immediately.
</Note>

Create also accepts an `Idempotency-Key` header. See [Idempotency](/concepts/idempotency).

## Getting and listing sandboxes

`GET /v1/sandbox/{sandbox_id}` returns the sandbox. `GET /v1/sandbox` returns a page:

- `page_size` — 1 to 100.
- `page_token` — the cursor from a previous page's `next_page_token`.
- `states` — filter by one or more states (repeat the parameter).

The response is `{ "sandboxes": [...], "next_page_token": "..." }`.

<Warning>
`deleted` is not a filterable state. A deleted sandbox is a tombstone, so list never returns it.
</Warning>

## Deleting a sandbox

<CodeGroup>
```shell cURL
curl -s -X DELETE "https://api.bonya.ai/v1/sandbox/$SANDBOX_ID" \
  -H "Authorization: Bearer $BONYA_API_KEY"
```

```shell CLI
bonya delete scratch
```

```ts TypeScript
await sandbox.delete();
```

```python Python
sandbox.delete()
```

```go Go
sandbox.Delete(ctx)
```
</CodeGroup>

**MCP:** `sandbox_delete`.

Delete returns `200` with the sandbox in state `deleted`. An unknown `id`, or one that belongs to a different organization than the caller's context, returns `404`.

## Network policy

A sandbox's `network` policy controls outbound egress. Its `mode` is one of:

- `open` (default) — unrestricted egress.
- `allowlist` — only the listed rules.
- `airgap` — no network access.

In `allowlist` mode the policy lists `allow` rules, each either a `domain` or a `cidr`. Change a running sandbox's policy with `PATCH /v1/sandbox/{sandbox_id}/network`, or `sandbox.updateNetwork(...)` in the SDKs.

```json
{ "mode": "allowlist", "allow": [{ "domain": "pypi.org" }, { "cidr": "10.0.0.0/8" }] }
```

## Fork

`POST /v1/sandbox/{sandbox_id}/fork` with `{ "count": 2 }` clones a running sandbox into that many new sandboxes. See [Snapshots](/concepts/snapshots).

## GPUs

List the GPU types and counts available to your organization with `GET /v1/sandbox/gpu-options` (`sandbox_gpu_options` over MCP, `listGpuOptions()` in the SDKs). An empty list means no GPU capacity is available. A GPU sandbox needs an `image` or an image template, and is subject to your organization's GPU limit.
