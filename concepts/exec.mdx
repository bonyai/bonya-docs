There are three distinct ways to run a command in a sandbox. Pick based on whether you need a single buffered result, a live interactive terminal, or a command that outlives the connection that started it.

| Mode | Endpoint | Use it when |
| --- | --- | --- |
| Buffered exec | `POST /v1/sandbox/{sandbox_id}/exec` | You want one command's exit code and output as a single JSON response. |
| TTY exec | `GET /v1/sandbox/{sandbox_id}/exec` (WebSocket) | You want an interactive, transient terminal for one command. |
| Managed sessions | `POST /v1/sandbox/{sandbox_id}/sessions` | You want a named command you can list, re-attach to, or kill independently of the connection that started it. |

## Buffered exec

```
POST /v1/sandbox/{sandbox_id}/exec
```

Synchronous, non-TTY, JSON request and response — no WebSocket upgrade involved. One JSON request, one JSON response; a non-zero exit code is still a `200` — check `exit_code` in the body.

<CodeGroup>
```shell cURL
curl -s -X POST "https://api.bonya.ai/v1/sandbox/$SANDBOX_ID/exec" \
  -H "Authorization: Bearer $BONYA_API_KEY" \
  -H "Content-Type: application/json" \
  -d '{"command": ["echo", "hello from bonya"]}'
```

```shell CLI
bonya exec $SANDBOX_ID -- echo "hello from bonya"
```

```ts TypeScript
const result = await sandbox.exec(["echo", "hello from bonya"]);
console.log(result.stdout, result.exitCode);
```

```python Python
result = sandbox.exec(["echo", "hello from bonya"])
print(result.stdout, result.exit_code)
```

```go Go
result, err := sandbox.Exec(ctx, "echo", "hello from bonya")
if err != nil {
    log.Fatal(err)
}
fmt.Println(result.Stdout, result.ExitCode)
```
</CodeGroup>

**MCP:** the `sandbox_exec` tool runs a buffered command the same way.

The request body:

<ParamField body="command" type="string[]" required>
  Argv to run. At least one element.
</ParamField>
<ParamField body="env" type="object">
  Environment variables to set.
</ParamField>
<ParamField body="working_dir" type="string">
  Working directory.
</ParamField>
<ParamField body="timeout_ms" type="integer">
  Timeout in milliseconds. The default is 60 seconds and the maximum is 10 minutes.
</ParamField>
<ParamField body="stdin_b64" type="string">
  Base64-encoded stdin to feed the process.
</ParamField>
<ParamField body="output_encoding" type="string">
  `utf8` or `base64`, controlling how `stdout`/`stderr` are encoded in the response.
</ParamField>

Response, always `200`:

<ResponseField name="exit_code" type="integer" required>
  The process's exit code.
</ResponseField>
<ResponseField name="signaled" type="boolean">
  Whether the process was terminated by a signal.
</ResponseField>
<ResponseField name="signal" type="integer">
  The signal number, if `signaled` is true.
</ResponseField>
<ResponseField name="took_ms" type="number" required>
  How long the command ran, in milliseconds.
</ResponseField>
<ResponseField name="stdout" type="string" required>
  Captured stdout, encoded per `output_encoding`.
</ResponseField>
<ResponseField name="stderr" type="string" required>
  Captured stderr, encoded per `output_encoding`.
</ResponseField>
<ResponseField name="stdout_truncated" type="boolean">
  Whether `stdout` was cut short.
</ResponseField>
<ResponseField name="stderr_truncated" type="boolean">
  Whether `stderr` was cut short.
</ResponseField>
<ResponseField name="output_encoding" type="string" required>
  `utf8` or `base64`, matching the request (or the server default).
</ResponseField>

<Warning>
A non-zero `exit_code` is still a **200 response** — it is not an API error. Buffered exec's HTTP status reflects whether the call itself succeeded (reached the sandbox, ran the command, and returned a result), not whether the command exited cleanly. Check `exit_code` and `signaled` in the body to determine command success; don't infer it from HTTP status. See [Errors](/concepts/errors) for what actually does produce a non-2xx response.
</Warning>

## TTY exec

```
GET /v1/sandbox/{sandbox_id}/exec
```

An HTTP upgrade to a WebSocket for a transient, interactive TTY session — one-off, not tracked as a named session. See [WebSockets](/concepts/websockets) for the protocol.

There's no raw cURL example for this mode — it's a WebSocket upgrade, not a single request/response — but the CLI and every SDK reach it directly.

<CodeGroup>
```shell CLI
bonya exec $SANDBOX_ID --tty -- bash
```

```ts TypeScript
const result = await sandbox.exec(["bash", "-lc", "stty size; printf done"], { tty: true, check: true });
console.log(result.stdout);
```

```python Python
result = sandbox.exec(["bash", "-lc", "stty size; printf done"], tty=True, check=True)
print(result.stdout)
```

```go Go
result, err := sandbox.ExecWithOptions(ctx, bonya.ExecOptions{
    Command: []string{"bash", "-lc", "stty size; printf done"},
    TTY:     true,
})
if err != nil {
    log.Fatal(err)
}
fmt.Println(result.Stdout)
```
</CodeGroup>

Streaming a TTY session (for full interactive forwarding, with resize) works the same way over each SDK's streaming call — see [Streaming exec](/guides/examples#stream-a-command-streaming-exec) for the non-TTY version of that pattern; pass `tty: true` (plus matching `cols`/`rows`) to get terminal semantics on the stream instead.

There's no MCP tool for TTY exec — [MCP tools](/mcp/tools) notes the WebSocket `exec` and session `attach` endpoints don't fit a request/response tool call; `sandbox_exec` is buffered-only.

## Managed sessions

For a command that should persist and be addressable by name independent of any single connection — list it, re-attach to it later, kill it explicitly — use a managed session instead of either exec mode. See [Sessions](/concepts/sessions).
